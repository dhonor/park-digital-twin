# 双引擎与云原生的可行性评估

> 定位：**不是要现在做**，而是把「什么时候值得做、要做哪些改造、代价多少」提前写清楚。
> 本文不改 `ADR-1`（Cesium 主引擎）与 `ADR-3`（不做微服务）的结论，只把它们留的「推翻条件」细化成**可判定的阈值 + 改造清单**。

---

## 0. 结论先行

可行性分级：**A** 现在就能做且划算 · **B** 条件可行（条件见正文） · **C** 当前体量下负收益

| 议题 | 分级 | 一句话结论 |
| --- | --- | --- |
| 离线仿真 + 结果回写（UE 算、Cesium 播） | **A** | 最划算的双引擎形态，且本仓库已有承接点（3D Tiles / 时序推送） |
| 容器化（单机 Docker / compose） | **A** | 1 人日，随时可做，见 `docs/03` 附录 |
| 双引擎「像素流全屏」 | **B** | 只有「整个场景都要影视级且要实时交互」才成立；12 栋楼的园区不值 |
| 双引擎「透明画布叠加」 | **B−** | 技术上能做，但 **alpha 通道编码不稳定 + 深度不通**，是长期隐患 |
| API 无状态化（多副本前置条件） | **B** | 3–5 人日，做了才有水平扩展的资格 |
| K8s + 微服务拆分 | **C** | 单园区、< 20 终端时纯增加运维成本；多点位/多租户再谈 |

判断依据始终是那条：**以场景定引擎，不以先进定引擎**。像素流不是「更高级的 Cesium」，它是另一种成本结构。

## 1. 双引擎：三种形态的代价差一个数量级

### 形态 A：像素流全屏（Cesium 让位给 UE）

UE5 Pixel Streaming / Unity Render Streaming → WebRTC → `<video>` 铺满视口，DOM 面板仍由前端框架渲染。

| 项 | 量级 | 说明 |
| --- | --- | --- |
| 显存 | 3–4 GB / 路（1080p60） | 每路独占一个引擎实例上下文 |
| GPU 密度 | 数据中心卡约 2–4 路/卡 | 消费级卡无 NVENC 并发授权，不适合多路 |
| 延迟 | 局域网 40–80 ms，公网 100–200 ms | 需 TURN 中继，弱网还要降码率/分辨率 |
| 交互 | 全部点选在 UE 内完成 | DOM 面板靠 DataChannel 事件回传 |
| 拾取 | 需要 UE 侧射线拾取 → 回传 assetId | 与现有 `building:/device:` 命名必须打通 |

**判据**：只有当「整个园区都要影视级材质/真实光影/物理效果，且必须实时交互」时才成立。
本项目的核心诉求是**空间关系 + 业务状态**（哪栋楼、哪台设备、什么指标），像素流解决不了这些，只会把首屏从 2 秒变成 30 秒。

### 形态 B：画面叠加（Cesium 打底 + UE 局部透明层）

这是很多方案的默认想象，但有几个硬问题：

| 硬问题 | 具体表现 |
| --- | --- |
| **alpha 通道不稳定** | WebRTC 的 VP9 alpha / HEVC alpha 在浏览器端支持碎片化；工程上常用绿幕抠像，遇到玻璃幕墙、树叶边缘必露馅 |
| **深度不通** | Cesium 的体块与 UE 的模型无法互相遮挡，设备点位会「浮」在精模前面 |
| **相机同步精度** | 需 30 Hz 同步 lon/lat/height/heading/pitch + 垂直 FOV，且两端投影必须完全一致，否则边缘错位 1–2 px 就能看出来 |
| **两套性能预算** | 同一帧里 Cesium 和 UE 都要跑满，低配一体机直接崩 |

> **注意与 ADR-1 补充的区别**：本仓库已在用的 Three.js 叠加画布**不属于**这里说的「不可靠叠加」。
> 差别在于：Three.js 层是**画布级**叠加，相机矩阵每帧从 Cesium 直接同步、两套 eye space 同构，且只渲染**单个孤立物体**、主动承认无深度互通并做宿主楼栋透明化（`ADR-1` 补充第 1–3 条边界）。
> 而 UE 像素流是**视频级**叠加：拿到的是编解码后的一帧画面，深度、alpha、相机矩阵都不在自己手里。

**建议**：不要做「同一屏两个视频级引擎混合」。真要做，改成**场景切换**——宏观用 Cesium，进入楼栋/设备页后整屏切 UE，退出再切回。切换点由业务定义，而不是由像素合成定义。

### 形态 C：离线仿真 + 结果回写（推荐先做）

UE 或专业求解器跑 CFD / 人流疏散 / 日照 / 消防烟羽，把**结果**导成 3D Tiles（`pnts`/`b3dm`）或时序 JSON，Cesium 负责播放与查询。

| 项 | 说明 |
| --- | --- |
| 实时协同 | 零 |
| GPU 常驻 | 零 |
| 本仓库承接点 | 3D Tiles 挂载（`docs/04`）、时序推送协议（`docs/02`）、`/api/layers` 的 LOD 管线 |
| 典型产物 | 每 5 分钟一个体素网格 / 每帧一个 pnts 帧序列 / 每小时的疏散人数曲线 |

**这是 A 级可行项**：观感提升明显（真实烟气、真实光影），成本是一次性渲染 + 存储，不改变在线架构。

## 2. 双引擎落到本仓库的改造点

如果真要上形态 A/B，需要新增的东西（其余不动）：

| 模块 | 现状 | 需要新增 |
| --- | --- | --- |
| 坐标系 | 已有 ENU 约定（`ADR-1` 第 2 条），顶点用米表达 | UE 侧 `GeoReferencing` 对齐**同一原点与同一 ENU 约定**，否则整体偏移 |
| 相机 | `scene.ts` 已持有 camera 状态 | 新增 WS 消息 `camera.state`（30 Hz：lon/lat/height/heading/pitch/fov/aspect） |
| 拾取 | `scene.pick` + `buildings:/devices:` id | video 层 DOM 事件 → 归一化坐标 → DataChannel → UE 反投影 → 回传 `assetId` |
| 资产编码 | `B01` / `DEV-B01-001` 已在全链路一致 | UE 端必须沿用同一编码，否则点选后查不到台账 |
| 部署 | 单容器 | GPU 节点 + TURN + 码率自适应 + 会话排队（并发 > GPU 路数时） |

一句话：**双引擎的成本不在渲染，在「两套坐标系 + 两套拾取 + 两套状态」的长期对齐**。

## 3. 云原生：先看现状，差距在「有状态」

当前是**单进程 + 有状态**，直接加副本会立刻出现四类问题：

| 组件 | 现状 | 多副本后的问题 | 改造 |
| --- | --- | --- | --- |
| 遥测广播 | 进程内 `set[asyncio.Queue]` | 终端连到不同副本，收到的设备状态不同 | Redis Pub/Sub |
| 设备状态 | 进程内 `_state` 字典 | 每副本各自模拟/各自漂移 | 状态入 Redis 或由 IoT 接入层单点写入 |
| TTL 缓存 | 进程内字典（≤512 项） | 命中率被副本数除，冷启动抖动 | Redis（**键空间设计不变**，`layer:{key}:{lod}:{bbox}`） |
| 告警 ack | 进程内字典，重启丢失 | ack 只在某个副本生效 | 落库 `dt_alarm.acked_at` |
| 静态资源 / 瓦片 | FastAPI 进程托管 `dist` 与 `/tiles` | API 进程被大文件拖死，扩缩容无意义 | 对象存储 + CDN / 独立 Nginx |
| 停机 | 直接退出 | WS 长连接被硬切，前端重连风暴 | 优雅停机：先摘流量 → 排空 WS → 退出 |

**结论**：云原生的真正门槛不是 K8s，而是**把有状态部分外置**。这一步做完，单机多副本就能跑，K8s 只是编排手段。

## 4. 分阶段路线

| 阶段 | 内容 | 工作量 | 验收指标 |
| --- | --- | --- | --- |
| **P0 容器化** ✅ | 多阶段 Dockerfile（Node 构建 → Python 运行）、`compose` 一键起 api + postgis（Redis 属于 P1，届时一并接入，现在放进去只会是个没人用的容器） | 1 人日 | `docker compose up` 后 `/api/health` 200，镜像 < 400 MB |
| **P1 无状态化** ✅ | 缓存/广播/设备状态外置到 Redis、ack 落库、Nginx 网关轮询（静态资源仍在镜像内，见 §4.1 说明） | 3–5 人日 | 2 副本下 WS 消息一致率 100%，KPI 不抖 |
| **P2 编排** | Deployment + HPA + readiness/liveness + 滚动更新 + Ingress（WS 需 `sessionAffinity` 或用 Redis 广播后无需粘滞） | 3–5 人日 | 滚动发布期间 0 次 5xx，扩缩容 60 s 内完成 |
| **P3 多租户** | `park_id` 维度、配额、按租户隔离缓存键与瓦片路径 | 视业务 | 单集群承载 ≥ 2 个园区互不干扰 |

P0 与 P1 的具体实现见 `docs/03-环境与部署.md` 的容器化附录；下文记录 P1 做成了什么、怎么验证的。

### 4.1 P1 落地记录（已实现并验证）

四处进程内状态全部外置，`REDIS_URL` 为空时行为与改造前完全一致：

| 能力 | 实现 | 关键取舍 |
| --- | --- | --- |
| 缓存 | `MemoryCache` / `RedisCache` 同一套 async 接口，键空间不变（`layer:{key}:{lod}:{bbox}:{limit}`） | 接口统一 async，避免切后端时改业务代码 |
| 事件广播 | leader 写 `park:events`，各副本订阅后转给本进程的 WS 队列 | WS 侧代码零改动，仍是从本地队列取 |
| 设备状态 | Redis Hash `park:telemetry:state` + `SET NX PX` 租约选主 | 只有 leader 推进模拟器；否则两个副本各跑随机游走，同设备两处显示不同值 |
| 告警确认 | `dt_alarm.acked_at` 落库 + 1 秒节流回读 | 比给每个 ack 做一次广播简单，且不会漏消息 |

**踩到的三个坑**（都已修）：

1. **导入脚本每次启动 `DELETE FROM dt_alarm`**，把 `acked_at` 一起抹掉 → 改成「只删源里已不存在的 id」+ upsert 不动 `acked_at`。
2. **运行期告警只在 leader 内存里**，其他副本 `/api/alarms` 少几条 → 广播回来的 `alarm` 事件也入各副本列表（按 id 去重）。
3. **端口段分配在并发启动时冲突**（`8000-8001:8000` 给两个副本分错端口）→ 改为 api 不暴露端口，加 Nginx 网关按 DNS 每 10s 重解析，扩缩容无需重启网关。

**实测结果**（2 副本 + PostGIS + Redis）：

```
网关轮询    8 次请求命中 2 个不同实例（4 / 4）
设备状态    DEV-B01-001/002/003 两副本完全一致（87.84 / 4.0 / 28.51）
选主        lease 唯一（telemetry-xxxxxxxx），Redis 状态字段 200
WS          两条连接各收到 10 条遥测，内容完全一致；Redis 订阅者数 = 2
告警确认    api-1 ack → api-2 1 秒内变 acked；重启 api-2 后仍为 acked
告警条数    api-1 = api-2 = 7
回归        单进程（无 Redis）18 passed / 4 skipped；接 PostGIS 22 passed
```

**没做的部分**：静态资源与瓦片仍在镜像内由 FastAPI 托管。多副本下这不影响正确性（每个副本都有文件），只影响效率——真要瘦身就把 `dist` 与 `tileset` 挪到对象存储 + CDN，属于 P1 的「附加项」而非前置条件。

## 5. 成本量级（人民币/月，仅量级参考）

| 形态 | 成本 | 适用 |
| --- | --- | --- |
| 单机容器（4C8G） | 200–500 | 单园区、< 20 终端 ← **本项目当前** |
| K8s 最小集群（3 节点 + 托管控制面） | 1500–3000 | 多环境、需要灰度与自愈 |
| GPU 像素流（L4 级，2 路/卡） | 1500–3000 / 卡 | 常驻 2 路 1080p；4 路即翻倍 |
| 对象存储 + CDN（瓦片 10 GB，日流量 100 GB） | 100–300 | 所有形态都建议尽早做 |

对比很直白：**给本项目上 GPU 像素流的月成本，是现在整台服务器的 5–10 倍，而业务侧不产生新能力。**

## 6. 触发条件（可判定阈值）

| 决策 | 触发条件（任一） | 不触发的典型特征 |
| --- | --- | --- |
| 上双引擎（形态 A） | ① 需要实时物理仿真（烟羽、疏散、风环境）并可交互；② 对外招商/汇报要求影视级且必须实时；③ 需要单台设备拆解演示 | 主要动作是「看园区、点楼、看指标」 |
| 上形态 C（离线仿真） | 有仿真结果要展示、要能按时间轴回放 | 只要静态态势 |
| 容器化 P0 | 需要交付给第三方环境、需要一条命令复现 | 单人本地开发 |
| 无状态化 P1 | 并发终端 > 50；或要求滚动发布不中断 | 单园区 < 20 终端 |
| K8s P2 | 多环境 + 多园区（≥ 2）+ SLA 99.9% | 单机重启 30 秒可接受 |
| 微服务拆分 | 团队 > 8 人且模块发布节奏相互阻塞 | 单体 1 个服务就能维护 |

参考本项目的现状：0.47 km²、12 栋楼、200 台设备、7 个图层、TTL 缓存 ≤ 512 项——**每一条都远未触达阈值**。

---

## 7. 明确不做

- 不做「为了简历上写 K8s」而上 K8s；
- 不做三引擎并存（Cesium + Three.js + UE），每加一个引擎都要多维护一套坐标、拾取、性能预算；
- 不做「全场景像素流替代 GIS」——空间分析、图层检索、矢量化统计仍属于 GIS 侧；
- 不在没有仿真结果的前提下引入 UE。

## 8. 与既有 ADR 的关系

| ADR | 原结论 | 本文补充 |
| --- | --- | --- |
| ADR-1 渲染引擎 | Cesium 主引擎，Three.js 只做局部增强 | 双引擎的三种形态与代价；**叠加画布不可靠**，要做就做场景切换 |
| ADR-2 轻量化 | 数据侧优先，LOD 不入库 | 不变；离线仿真产物同样走 3D Tiles + LOD |
| ADR-3 后端 | PostGIS 起步，GeoServer 按需，**不做微服务** | 保留「不做」，补上「先无状态化、再编排」的条件与改造清单 |

三条 ADR 的结论都没有被推翻，只是把「以后会不会变」变成了**可判定、可预算的路线**。
