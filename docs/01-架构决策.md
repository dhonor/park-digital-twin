# 架构决策记录（ADR）

> 三条硬约束：**以场景定引擎**、**数据轻量化优先于渲染优化**、**后端从开源栈起步按需演进**。
> 本文只回答「为什么这么选」和「什么条件下推翻」。

---

## ADR-1 渲染引擎：CesiumJS 主引擎，Three.js 只做局部增强，不引入 OpenLayers

### 先看场景，不看技术热度

| 场景事实 | 对引擎的硬要求 |
| --- | --- |
| 园区 0.47 km²，需要真实经纬度与真实方位 | 内置地理坐标系、椭球、投影 |
| 输入是 GIS 数据（楼栋面、管网线、设备点、绿地水系） | 直接消费 GeoJSON / WMS / 3D Tiles |
| 交互是「点楼栋看详情、开关图层、楼层剖切」 | 屏幕拾取（picking）与实体属性绑定 |
| 大屏常态是宏观态势，不是室内漫游 | 2.5D 拉伸体块足够，不需要 PBR 影视级 |
| 需要 2D/3D 视图切换（汇报用平面图） | 同一场景内切换视图模式 |

### 方案对比

| 方案 | 优势 | 落到本场景的代价 | 结论 |
| --- | --- | --- | --- |
| **CesiumJS** | 坐标系 / 瓦片调度 / 空间拾取 / 2D-3D 切换全部内置，GeoJSON 一行接入 | 单栋建筑内部细节表达弱 | **主引擎** |
| Three.js | 渲染自由度高，材质与后期强 | 没有坐标系、没有瓦片、没有拾取；要自己补一套 GIS 层，等于重写半个 Cesium | 不做主引擎 |
| Cesium + OpenLayers | 2D 专题制图、打印出图能力强 | 双引擎的相机、图层、坐标系要长期同步维护；而 Cesium 自带 `SCENE2D` | 本期不引入 |
| Cesium + Three.js 混渲染 | 设备级高模（冷水机组、风机）可以做到零件级 | 需相机矩阵同步 + 无法共享深度缓冲 | **已接入，限定在设备级** |

### 落地方式

- 引擎相关代码集中在 `frontend/src/cesium/scene.ts`，对外只暴露 `setLayer / updateDevices / selectBuilding / setFloorClip / morph` 等方法。
- React 只负责 UI 与数据，不直接操作 Cesium 对象，避免「组件里到处 `viewer.entities.add`」的烂尾结构。

### ADR-1 补充：设备级高模为什么用叠加画布而不是自定义 Primitive

选中设备时，除点位之外再渲染一台 2~3m 的实体设备（冷水机组 / 水泵 / 配电柜 / 立杆摄像机…），由 Three.js 负责。

| 实现方式 | 为什么不用 / 为什么用 |
| --- | --- |
| Cesium `Primitive` + Three.js 离屏渲染当纹理 | Cesium 不对外开放第三个渲染通道，只能「渲染到纹理 → 贴到屏幕四边形」，多一次全屏拷贝，且依然拿不到深度缓冲 |
| **独立透明画布叠在 Cesium 之上** | 零拷贝；可独立开抗锯齿与色调映射；相机矩阵每帧从 Cesium 同步，两套 eye space 都是「x 右 / y 上 / -z 前」，矩阵可直接互换 |

三条必须守住的边界，否则这套混渲染会变成技术债：

1. **只做局部，不做全场景**：Three.js 层没有地球、没有瓦片调度，200 台设备的高模绝不能常驻，只在选中单台设备时挂载一次，切走立即 `dispose` 几何与材质。
2. **坐标一律走局部 ENU**：模型顶点用「米」表达，`view_three = view_cesium × 局部系→ECEF`，避开 ECEF 6.4e6 量级的浮点精度损耗。
3. **承认没有深度互通**：叠加画布永远画在 Cesium 之上。因此进入设备视角时会把宿主楼栋临时透明化（只留轮廓与标签），既解决「相机在体块内部、整屏糊成楼栋色」，也避免高模穿模的观感问题。

相机取景的两个坑记在这里，改这块时先看：`screenSpaceCameraController.minimumZoomDistance` 会把低于该高度的机位沿视线顶回去（原值 25m，设备视角需要 20~30m，已下调到 6m）；楼栋间距只有 20~30m，定距环绕的落点经常正好在隔壁楼体块里，机位必须是「水平退距 + 俯角」反算，并对落点做楼栋碰撞后抬高。

### 什么时候推翻这个决策

| 触发条件 | 动作 |
| --- | --- |
| 主要场景变成楼内漫游 / 设备拆解 / 工艺仿真 | 引入 Three.js，作为 Cesium 的自定义 Primitive 插件 |
| 主要场景变成规划对比、图册出图、规划审批 | 引入 OpenLayers，用 2D 视图而非双引擎同步 |
| 需要接入倾斜摄影 / 精细化 BIM | 转 3D Tiles（Cesium 原生支持，无需换引擎） |

## ADR-2 数据轻量化优先于渲染优化

### 核心判断

园区级孪生的首屏体验瓶颈几乎从来不是 GPU，而是**首包体积**。
一栋楼的 BIM 精模 20–200 MB，而同一栋楼的「体块 + 属性」只有 3–5 KB。
先把数据做轻，渲染自然就快；反过来优化 drawcall 是舍本逐末。

### 四级 LOD（服务端生成，不入库）

| LOD | 使用场景 | 几何 | 坐标精度 | 属性 |
| --- | --- | --- | --- | --- |
| LOD0 概览 | 园区全景 / 大屏轮播 | 8 m 抽稀，面要素用包络框 | 4 位（≈11 m） | 仅标识与高度 |
| LOD1 标准 | 日常巡检 / 单栋浏览 | 1.5 m 抽稀 | 5 位（≈1.1 m） | 业务主属性 |
| LOD2 精细 | 专题分析 / 上报归档 | 不抽稀 | 7 位（≈1 cm） | 全属性 |

### 四步管线（`backend/app/services/lightweight.py`）

1. **几何抽稀**：Douglas-Peucker。容差单位是米，先按纬度余弦压平等距再比较（踩过的坑：直接把 1.5 当成 1.5 度，170 m 的楼会被压成一条线）。
2. **包络框替代**：仅 LOD0 的面要素，用 4 角点包围盒代替真实轮廓。
3. **坐标量化**：按 LOD 保留小数位，直接减小 JSON 体积。
4. **属性白名单**：按图层 × LOD 裁剪字段。GIS 数据里属性往往比几何还大。

外加一条运行时策略：**按视口 bbox 增量拉取**（`/api/layers/{key}?bbox=...`）。

### 实测（本仓库种子数据，`GET /api/lightweight/report`）

| LOD | 原始 JSON | 轻量化后 | JSON 降幅 | gzip 降幅 |
| --- | --- | --- | --- | --- |
| LOD0 | 101.0 KB | 45.9 KB | 54.5% | **62.1%** |
| LOD1 | 101.0 KB | 82.3 KB | 18.5% | 22.4% |
| LOD2 | 101.0 KB | 93.9 KB | 7.0% | 5.2% |

> LOD1/LOD2 降幅小是**如实反映**：这份种子数据本身就是轻量 GeoJSON。
> 换成 CAD/倾斜摄影衍生的原始数据，几何抽稀那一档的收益会显著放大。

### 纪律

- **数据库只存一份原始要素**，LOD 在服务层实时生成。绝不把三套精度落库——那是三份数据源的开始。
- 前端「视图精度」切换会真实重新拉取数据，而不是只改渲染参数；面板上的降幅是这次请求的实测值。
- 楼栋明细（分层面积、房间、能耗曲线）走独立接口 `/api/buildings/{id}`，点开才拉，不混进图层。

### 什么时候升级

| 触发条件 | 动作 |
| --- | --- |
| 单园区要素 > 5 万，或需要视锥流式加载 | 生成 3D Tiles（B3DM）/ 矢量瓦片，替代 GeoJSON 全量下发 |
| 建筑需要真实外立面与内部结构 | 倾斜摄影 + BIM 轻量化，仍然走 LOD 分级 |
| 设备数 > 5000 | 点位改用 Primitive 批量渲染或瓦片化点位 |

## ADR-3 后端：PostGIS 起步，GeoServer 按需上，不做微服务

### 起步形态

```
FastAPI (Python 3.13)
  ├── repository/memory.py   ← 零依赖回退，直接读 data/*.geojson
  └── repository/postgis.py  ← 配 DATABASE_URL 即切换，接口完全一致
服务层
  ├── lightweight.py         ← LOD 管线
  ├── telemetry.py           ← 遥测状态机 + WS 广播
  ├── alarms.py              ← 告警合并与确认
  └── cache.py               ← 进程内 TTL（多实例时换 Redis）
```

### 为什么不是「PostgreSQL + PostGIS + GeoServer」一步到位

| 维度 | GeoServer | 自研轻量 API |
| --- | --- | --- |
| 交付内容 | WMS/WFS/WMCS 标准服务 | 前端要的 GeoJSON + LOD |
| 部署成本 | 独立 JVM 进程 + 数据目录 + 样式（SLD） | 与业务 API 同进程 |
| 轻量化能力 | 依赖 SLD 与 `ST_Simplify` 配置 | 代码里可控，能返回压缩指标 |
| 适合谁 | 第三方 GIS / 上级平台 / ArcGIS 客户端 | 自有前端 |

园区级项目 90% 的时间只有自家前端在取数，GeoServer 是**集成需求**才需要的中间件，不是起步必需品。
所以：

- 默认走自研 API，数据库用 PostGIS（真正需要的是空间索引与 `ST_*` 能力）。
- 需要对外提供 OGC 服务时，`docker compose --profile ogc up -d` 起 GeoServer，与业务 API 并存，互不影响。
- 前端通过 `/api` 取数，后端换实现（内存/PostGIS/瓦片服务）前端零改动。

### 数据表设计取舍

统一要素表 `dt_layer_feature (layer_key, feat_id, props jsonb, geom geometry)`：

- 园区级数据量（万级要素）下比「一层一表」更好维护，图层增减只是数据行变化；
- 属性放 jsonb，字段演进不需要 DDL；
- 需要强约束/高频查询的属性再抽列或建表达式索引；
- 真出现性能瓶颈，再按图层拆表或切矢量瓦片（`pg_tileserv` / `Martin`）。

### 演进路线

| 阶段 | 触发条件 | 动作 |
| --- | --- | --- |
| 0 演示 | 无 | 内存仓库，`python tools/gen_demo_data.py` 即跑 |
| 1 单园区 | 需要持久化与并发写入 | PostGIS + `load_postgis.py` |
| 2 多园区 | 出现第二、第三个园区 | 增加 `park_id` 维度与租户隔离 |
| 3 数据量上来 | 要素 > 5 万 / 首包 > 1 MB | 矢量瓦片或 3D Tiles |
| 4 真实 IoT | 设备上报量 > 10 万点/天 | MQTT 接入 + 读数表按月分区（或 TimescaleDB） |
| 5 对外集成 | 上级平台按 WMS/WFS 取图 | 启用 GeoServer profile |

**明确不做**：Kafka、K8s、微服务拆分。0.47 km²、200 台设备的体量上这些，只会让交付周期翻倍。

> 什么时候改主意、要改哪些地方、代价多少，见 [`docs/05-双引擎与云原生可行性.md`](05-双引擎与云原生可行性.md)：那篇把「不做」展开成了可判定的触发阈值（并发终端数、园区数量、SLA）与改造清单（缓存/广播外置、ack 落库、静态资源外移）。

## 附：一次真实踩坑记录（保留，避免重复）

1. **抽稀容差单位错用**：把米当度，`tolerance=1.5` 相当于 166 km，所有楼栋被压成 2 个点。修复：`tolerance / 111320` 并做经度余弦压平。
2. **相机用 `flyTo` 初始化**：首帧动画未推进时相机会停在默认全球视角，场景全黑。修复：首帧用 `setView`。
3. **相机只给高度不给目标点**：相机悬在园区正上方朝前看，园区落在视野外。修复：按「目标点 + 距离 + 俯角」计算 ENU 偏移，距离由园区跨度反推。
4. **设备坐标二次换算**：生成器把已是经纬度的值又当成米制偏移换算，200 台设备全部塌缩到一个点。修复：直接写经纬度。
5. **`disableDepthTestDistance` 用 `POSITIVE_INFINITY`**：在部分 WebGL 实现下点位被丢弃。修复：改用一个足够大的有限值（2000 km），语义相同。
6. **切换平面视图后看不见园区**：两层原因叠加。① 2D 是正交投影，相机沿用 3D 的斜视角投影位置；② Cesium 的异步 morph 依赖连续帧推进，低帧率或后台标签页下会**卡在 `MORPHING`**，相机停在半路、`morphComplete` 永不触发，画面全黑。修复：改用 `morphTo2D(0)` / `morphTo3D(0)` 瞬时切换，切完立刻用园区矩形 `setView` 重新框定，过渡观感交给 UI 遮罩；同时保留 `completeMorph()` 兜底，并在已是目标模式时直接返回（重复调用 `morphToX` 会让状态机卡死）。
7. **建筑名称有锯齿**：`Viewer` 默认 `useBrowserRecommendedResolution: true` 会忽略 `devicePixelRatio`，SDF 文字在 1× 画布上渲染后被拉伸。修复：关闭该选项启用 DPR 渲染 + `FXAA`，低 DPI 屏再叠 1.25× 超采样。副作用是所有线宽/点径/标签内边距都变成帧缓冲像素，需统一乘以 `dpr × 超采样` 补偿，否则高分屏上线会变细、点会变小。
8. **诊断函数把页面搞崩**：`debugInfo()` 里读 `camera.positionCartographic`，而 2D 模式下该值为 `undefined`，紧随其后的 `toDegrees` 抛出 `DeveloperError: radians is required`，被图层装载的 try/catch 捕获后**整层数据不再装载**——现象就是「数据加载不对」。修复：按模式分支取相机状态并整体 try/catch，错误提示同时保留完整堆栈（悬停可见）。
9. **「数据好像不对」的三处真实来源**：① 快速连点楼栋/设备，先发后到的响应会覆盖后点的内容 → 加请求令牌，只认最后一次；② 接口响应被浏览器启发式缓存，切 LOD 后回放旧 JSON → `/api` 统一 `Cache-Control: no-store`，缓存只放服务端；③ 切 LOD 会重建实体，选中高亮与楼层剖切被重置，面板却仍显示旧状态 → 实体重建后恢复选中态与剖切高度；图层也改成「全部到齐再统一装载」，避免一半旧 LOD 一半新 LOD 的中间态。
10. **「切换视图精度没区别」**：接口确实换了数据（LOD0 60 点/4 属性 vs LOD2 62 点/9 属性），但示例数据几乎全是轴对齐矩形——8m 抽稀和包络框在视觉上等于没变，功能看起来就是坏的。修复三件事：① 让一部分楼栋带折角/切角、水体用 56 点曲线轮廓，抽稀才有东西可抽；② 标签按当前 LOD **真实存在的属性**渲染（概览只有楼名、标准加层数、精细再加建筑面积），不造假数据；③ 切换后弹一条实测提示（要素数 / 传输量 / 降幅），把「看不见的收益」变成可读的数字。
11. **缩放/平移时点位不跟着缩、画面有跳动**：三处「固定阈值」造成的。① 楼栋标签 `DistanceDisplayCondition` 上限写了 2600m，相机拉到 2600m 时所有标签同时消失；② 设备点位 `NearFarScalar(240, 1.35, 5000, 0.9)` 远景只缩到 0.9 且在 5000m 夹紧，视觉上点位几乎不随场景缩放，到夹紧点还会「卡」一下；③ 三维瓦片开了 `dynamicScreenSpaceError`，相机动的时候反复调瓦片取舍，几何体发「游动」。修复：标签上限提到相机最远距离（5200m）、点位缩放改为近 1.6 / 远 0.35 且夹紧点放到 3500m、关闭动态误差；并把楼栋材质改成按「颜色+透明度」缓存复用，避免悬停时反复 `new ColorMaterialProperty` 引起的一帧闪烁。
12. **PostGIS 路径第一次真正执行时连爆三个错**：① 表结构 `geometry(Geometry, 4326)` 是 2D，而园区要素都带高程 → `Geometry has Z dimension but column does not`，改成 `GeometryZ` 并在导入时 `ST_Force3D`（同时用 `DROP VIEW` + `ALTER COLUMN ... USING ST_Force3D` 兼容已建好的旧库）；② `SELECT jsonb_build_object('name', $1, ...) WHERE layer_key = $1` 让 Postgres 推不出参数类型 → `AmbiguousParameterError`，参数需显式 `$1::text`；③ asyncpg 的 `timestamptz` 只收 `datetime` 对象，传 ISO 字符串直接报错 → 导入时 `datetime.fromisoformat`。**结论：一条没被真正跑过的链路等于没写**，所以补了 `tests/test_postgis.py`，无库自动跳过、有库必须过。
